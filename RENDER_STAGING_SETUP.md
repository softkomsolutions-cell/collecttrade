# Render Staging Setup

This runbook is the fastest path from the current local repo to a stable public staging URL for partner testing.

## Goal

Create one public staging environment that:

- serves frontend and backend together
- uses the current Docker setup
- exposes a stable Render URL
- supports partner testing and the in-app feedback board

---

## 1. Preconditions

Before starting:

1. the latest code is pushed to GitHub
2. the repo includes:
   - `Dockerfile`
   - `render.yaml`
   - `server/.env.example`
3. local checks pass:

```powershell
cd C:\Users\Darren\collecttrade
npm run check
```

---

## 2. Create the Render Service

1. Sign in to [Render Dashboard](https://dashboard.render.com/)
2. Click `New`
3. Choose `Blueprint`
4. Connect the GitHub repo:
   - `softkomsolutions-cell/collecttrade`
5. Render should detect:
   - `render.yaml`

Expected service shape:

- name: `collecttrade-staging`
- runtime: `docker`
- region: `frankfurt`
- plan: `starter`
- health check path: `/api/health`

---

## 3. Environment Variables

Render should create or accept:

- `PORT=5000`
- `NODE_ENV=production`
- `AUTH_SECRET` -> generated by Render
- `CONNECTOR_SECRET` -> generated by Render
- `TWELVE_DATA_INTERVAL=1h`
- `TWELVE_DATA_JSE_SYMBOL=JTOPI`

Optional:

- `TWELVE_DATA_API_KEY`

Recommendation:

- leave `TWELVE_DATA_API_KEY` blank for the first staging deploy if the goal is simply partner access and UX feedback
- add it later when you want live candles in staging

---

## 4. Persistent Disk

The current Blueprint includes:

- disk name: `collecttrade-data`
- mount path: `/app/server/data`

Why it matters:

- preserves app state between restarts
- keeps feedback board and local persisted data from resetting on every deploy

Note:

- this is one reason the Render `starter` plan is being used for staging

---

## 5. First Deploy Check

After Render finishes:

1. open the Render service URL
2. confirm the app shell loads
3. open:

```text
/api/health
```

Expected result:

- HTTP `200`

---

## 6. Smoke Test

Run the built-in smoke test against the Render URL:

```powershell
cd C:\Users\Darren\collecttrade
npm run render:smoke -- https://your-render-url.onrender.com
```

This checks:

- `/`
- `/api/health`
- `/api/signals`
- `/api/news`

What success looks like:

- root app shell responds
- health responds
- signals return items
- news returns items

---

## 7. Partner Testing Checklist

Once staging is live:

1. create a test account
2. confirm sign-in works
3. confirm service menu opens
4. confirm `News`, `Trade`, `Collectibles`, `Portfolio`, and `Reports` open cleanly
5. confirm `Settings -> Feedback Board` is usable
6. share the URL with partners

Suggested partner route:

1. onboarding / menu
2. News
3. Trade
4. Collectibles
5. Reports
6. Settings -> Feedback Board

---

## 8. Recommended First Staging Use

Use the first Render staging round mainly for:

- app feel
- navigation clarity
- product trust
- usefulness of dashboards and reports
- structured partner suggestions

Do not treat the first staging round as the final launch environment.

---

## 9. After Staging Is Working

Once Render staging is stable:

1. collect partner feedback
2. refine UX and retention features
3. complete live-data and execution trust work
4. evaluate South African production hosting before go-live

That keeps staging and production decisions separate, which is the healthier path for the product.
